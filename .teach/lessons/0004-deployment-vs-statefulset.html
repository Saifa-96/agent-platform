Deployment 与 StatefulSet — pod 的两种管理员

约 15 分钟 · 前置：第 2、3 课（Deployment 你已实操过，本课重心：StatefulSet、三个名字辨析、NAP 用法对照）· 产出：判断任何服务该用哪种管理员，并说清 NAP 为什么两种都用

上一课结尾说：你写下期望状态"应该有 3 个 pod"，剩下交给收敛。这课回答：具体是谁在读这句话、按什么规则管 pod？K8s 里管 pod 的东西叫工作负载控制器（workload controller），你只需要认识两种——恰好 NAP 每种都用了一个。

注意：workload controller 不是 kubelet。它们是两层不同的循环：controller 住在 control plane，只负责"数副本数量，缺了就在账本里登记新 pod 对象"——纯记账，不碰容器；kubelet 住在每台机器上，读到"这个 pod 归我管"才真正拉镜像、启动容器。中间还有 scheduler 给 pod 挑机器。链条上没人直接调用谁，全靠改账本协作（上一课哲学的内部贯彻）。controller = 总部数人头的调度员，kubelet = 楼层管家。

↺ 自愈也是同一条链：pod 崩了 → 所在机器的 kubelet 重启它；整个机器挂了 → controller 发现账本里少了，重新走①②③在别的机器补上。没有"报警-修复"系统，只有永不停歇的循环。
这张图画的是角色分工，不是物理位置。在 k3d/k3s 单节点集群里，前台、账本、①②③全部住在同一个 k3s 进程里（那个 Docker 容器的主进程）；多节点集群里③每机各一个、①②和前台在 server 节点。"由谁控制物业？"——没人：容器主进程就是 k3s，Docker 的重启策略保它存活，k3d 只负责接生（建容器+写 kubeconfig 后退场）。最底层的结构与第 2 课同构：Docker 用声明式保 k3s 活，k3s 用期望状态保你的 pod 活。

「写下 Deployment」的具体形态：YAML 清单

"workload controller"一词指两层：控制器软件（K8s 自带的通用进程，所有 Deployment 共用一个，你不用写）和你的声明（一个 YAML 清单文件，你真正"写下"的东西）：

apiVersion: apps/v1
kind: Deployment        # 声明的种类："我要一个 Deployment"
metadata:
  name: my-agent        # ① 这份声明自己的名字
spec:                   # 期望状态：你真正"写"的内容
  replicas: 3           # ← 流程图里的"期望 3 副本"
  selector:
    matchLabels: { app: my-agent }  # ③ 认领标准：带此标签的 pod 归我数
  template:             # pod 的模子（第 1 课的图纸）
    metadata:
      labels: { app: my-agent }   # ② 出厂盖章：每个新 pod 自动带此标签
    spec:
      containers:
        - name: agent
          image: my-agent:1.0

提交：kubectl apply -f deployment.yaml → API server → etcd → 上面的链条开动。YAML 只是给人写的序列化格式（线上跑 JSON），程序可以跳过它直接构造对象——NAP 就是这样：internal/k8s-provider/static-workload.ts 里 createNamespacedDeployment(...) 用 TypeScript 构造对象直接提交，NAP 没人手写 YAML，写 YAML 的角色被 env-runner 的代码取代。YAML 语法不熟（缩进、列表的 "-"、对齐规则）时看速查卡。

清单里的三个名字：①名字、②盖章、③认领标准

上面标了 ①②③ 的三处极易混淆，它们各自管各自的事：① metadata.name 是这份 Deployment 档案自己的标题，作用仅限于让别人指名道姓地找到这份声明本身（kubectl get deployment my-agent）；② template.labels 是出厂时盖在每个新 pod 身上的标签；③ selector 是认领标准，controller 数副本数时数的正是符合这个查询的 pod。

①和②③之间没有任何语义关系——示例里都用 my-agent 纯属社区惯例（大家习惯把标签起成和应用同名），你完全可以用 prod-agent-2024 当名字、用 app: xixi 当标签，一切照常工作。真正存在硬性关系的是②和③：K8s 要求 selector 必须匹配 template 的 labels，否则模子造出的 pod 自己都不认领，账永远对不上，API 会直接拒绝。

这枚标签还是第 4 课的伏笔：Service 认领 pod 靠的也是 label。同一枚 app: my-agent 被 Deployment（数数）和 Service（转发名单）各自消费一次——这就是"同一套标签机制把两个对象缝在一起"的具体含义。

分水岭：副本可不可以互换

选哪种管理员，只看一个问题：你的多个副本（replica）是不是彼此等价的"无名氏"？

Deployment

app-7f9c8b-x2vklapp-7f9c8b-p9qz4app-7f9c8b-k3m8w
  • 副本无名、等价、可互换：名字带随机尾巴，谁死都一样，补一个就行
  • 内置滚动升级：新的起、旧的下，服务不中断；可回滚
  • 适合无状态（stateless）服务——典型的 Web API

StatefulSet

db-0db-1db-2
  • 副本有身份：稳定序号 0、1、2，死而复生还是原来的编号
  • 有序启停：按编号顺序起、按编号倒序停
  • 通常每个副本挂自己的盘——数据跟着身份走
  • 适合有状态（stateful）服务——典型的数据库
名字来历：Deployment = "一次部署"的名词化——你声明一次部署应有的样子。StatefulSet = stateful（有状态的）+ set（一组）——"一组有身份的东西"。判断口诀：**副本死了，随便补一个没人发现 → Deployment；副本死了，必须"还是它" → StatefulSet。**

为什么数据库需要身份？想象 PostgreSQL 主从：db-1 是从库、攒着自己的复制位点——它死了补一个全新 pod 进来没用，必须还是"db-1"、接上原来那份数据。身份+盘跟着走，这就是 StatefulSet 存在的理由。

NAP 的两种用法（真实代码）

先说业务：NAP 为什么需要两种 workspace？多租户平台要托管成百上千个 agent，而大部分 agent 大部分时间没人用——全都 7×24 跑着，平台在为闲置付费。于是 NAP 给用户一个开关（选一种）：static = 容器常驻、消息秒回、但 7×24 占资源，适合高频/关键 agent；auto-scaling = 副本跟需求走、没人用时缩到零（闲置零成本），代价是第一条消息要冷启动（≤90 秒），适合长尾 agent。这是典型的"钱 vs 延迟"的交易。

两种业务选择落到 K8s 上，恰好各用一种管理员，而且用法都不是教科书的典型形状：

static workspaceauto-scaling workspace
管理员Deployment（单副本）StatefulSet（1..N 副本）
卷一个 RWO PVC一块 RWX PVC，所有副本共享
为什么常驻单实例，最简单形状要稳定身份做会话亲和，不要独立盘
代码internal/k8s-provider/static-workload.tsinternal/k8s-provider/auto-scaling-workload.ts
会话亲和是什么？一个正在执行的 turn 存在于某一个副本的进程内存里；用户断线重连时，请求必须找回"还是那个副本"，否则现场就断了。普通 Service 的 VIP 是轮询分发，会把请求随机甩给任意副本——所以 auto-scaling 需要 StatefulSet 的稳定序号来实现"能点名找到某个副本"。完整机制（headless DNS、逐副本寻址）正是下一课的主题。

两个提前一分钟的词：RWO（ReadWriteOnce）= 卷同一时刻只能被一台机器（K8s 节点）挂载——注意限制单位是机器不是 pod：同机器上的多个 pod 可以共享，跨机器不行（挂载是机器内核执行的动作，pod 只是住在机器上用现成的）；RWX（ReadWriteMany）= 多台机器同时挂同一块卷（NFS 支持，因为数据真身在 NFS 服务器、各机器只挂网络客户端视图；块设备做不了——两个内核同写一个文件系统会损坏）。细节第 6 课展开。

注意 NAP 用 StatefulSet 的姿势：要了身份，没要独立盘。经典用法是"每副本一块自己的盘"（数据库），NAP 反着来——所有副本挂同一块共享卷。它图的只是稳定序号带来的稳定网络地址（第 4 课的主角）：一个会话被路由到副本 2，断了重连还能找到"还是副本 2"。这是对 StatefulSet 的创造性挪用，记住这个例子，比记住教科书定义有用。
