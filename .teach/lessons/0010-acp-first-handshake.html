Lesson 10 / ACP 模块 2/6 · 动手课

第一次握手 — 内存直连实验

约 30 分钟 · 前置：第 9 课 · 产出：一个能跑的 echo agent + 测试客户端，在内存里走完 initialize → new → prompt → update → stopReason 全程

第 9 课你在纸上看时序图；这一课让它活起来。方案是 SDK 的内存直连——client app 和 agent app 在同一进程里握手，不需要 WebSocket、不需要子进程、不需要任何基础设施。这是官方钦定的测试姿势（README 原话："useful for tests and in-process examples"），也是你将来给 adapter 写单测的形态。

先认识三个 API 角色（都验证自你装的 SDK）

① agent() —— 构建你的 Agent 侧 app

README 官方起手式：agent({ name }) 拿到构建器，.onRequest(方法, handler) 逐个注册你要响应的方法。**你是 Agent 侧** = 你响应 initialize / session/new / session/prompt，主动发 session/update。

② handler 的 ctx —— id 概念的代码化

每个 handler 收到一个 ctx，身上有三样东西，正好对应你学过的三种消息：

  • ctx.params —— 来件（对方 request 的参数）
  • 返回值 —— 回信：**你返回什么，SDK 自动把它变成同 id 的 response**。注意你从头到尾没写过 id——票根的贴和抄全被 SDK 包办了
  • await ctx.notify(methods.client.sessionUpdate, {...}) —— 发通知（无 id，发完就完）。处理 prompt 期间想推流式更新，就用它
③ clientApp.connect(agentApp) —— 内存直连

返回 ClientConnection，它的 .agent 就是"以客户端身份调对方"的把手：conn.agent.request(methods.agent.initialize, 参数)。测试客户端用它按剧本走流程。

实验骨架（在 agent-hub 里建文件）

在 agent-hub/internal/acp-adapter/examples/first-handshake.ts 创建文件（examples/ 是库的标准惯例；这个文件属于你的项目，不是课程内容）。骨架如下，四个 TODO 是你的：

import { agent, client, methods } from "@agentclientprotocol/sdk"

// ── Agent 侧：echo agent ──────────────────────────────

    .onRequest(methods.agent.initialize, (ctx) => ({
        protocolVersion: 1,
        agentCapabilities: {},
        authMethods: [],
        // TODO A：先原样返回这个最小响应，跑通后再加一项能力试试
    }))
    .onRequest(methods.agent.sessionNew, (ctx) => ({
        sessionId: "s-1",
        // TODO B：返回一个 sessionId（先写死，体会"会话由你创建"
        // 后续换成 crypto.randomUUID()）
    }))
    .onRequest(methods.agent.sessionPrompt, async (ctx) => {
        // TODO C：发 2~3 条 agent_message_chunk 通知，再返回结束
        // 形状：await ctx.notify(methods.client.sessionUpdate, {
        //   sessionId: ctx.params.sessionId,
        //   update: { sessionUpdate: "agent_message_chunk",
        //             content: { type: "text", text: "..." } },
        // })
        // 返回：{ stopReason: "end_turn" }
        // 进阶：把 ctx.params.prompt 里的用户文字原样分段 echo 回去
    })

// ── Client 侧：测试客户端（收通知）──────────────────────
const testClient = client({ name: "test-client" })
    .onNotification(methods.client.sessionUpdate, (ctx) => {
        // TODO D：打印收到的每条 update
        // 从 ctx.params.update 里取出 sessionUpdate 类型和内容
    })

// ── 内存直连 + 按剧本走流程 ────────────────────────────
const conn = testClient.connect(echoAgent)

const init = await conn.agent.request(methods.agent.initialize, {
    protocolVersion: 1,
    clientCapabilities: {},
})
console.log("握手完成:", JSON.stringify(init))

const { sessionId } = await conn.agent.request(methods.agent.session.new, {
    cwd: "/tmp",
    mcpServers: [],
})
console.log("会话建立:", sessionId)

const result = await conn.agent.request(methods.agent.session.prompt, {
    sessionId,
    prompt: [{ type: "text", text: "你好，ACP" }],
})
console.log("回合结束:", JSON.stringify(result))
conn.close()

运行（Node 24 原生支持直接跑 .ts，不需要任何装载器）：

cd agent-hub/internal/acp-adapter
node examples/first-handshake.ts
# 若报模块解析错，把 "type": "module" 检查一下（包里已有），或加 .mts 后缀

验收清单（四条全过）

  1. 终端按顺序输出：握手完成的 agent 能力 → 会话 id → 若干条 [update]（你的通知逐条到达） → 回合结束 stopReason: end_turn
  2. update 的打印顺序和你 notify 的顺序一致——顺序即意义
  3. 能口头回答：response 是谁造的？（你没写 id，SDK 把返回值配了对）
  4. 进阶完成的话：echo 的内容来自用户 prompt，不是写死的

检索练习

1. handler 的返回值最终变成了什么？
  1. 一条通知推送
  2. 同 id 的 response
  3. 下一条的参数
  4. 连接关闭信号
2. prompt handler 里推流式更新用 ctx 的什么？
  1. ctx.notify
  2. ctx.request
  3. ctx.respond
  4. ctx.stream
3. 内存直连和将来 Zed 的 ws 直连，差在哪一层？
  1. 方法集合不同
  2. 信封格式不同
  3. 会话模型不同
  4. 只差传输层
4. initialize 的响应里必须让客户端知道的核心信息是？
  1. 服务器的价格
  2. 可用的模型表
  3. 协议版本与能力
  4. 用户的余额
