Lesson 08 / 会师点（先学完 0001–0007 基础件）

从零开始写一个 agent-platform — 施工顺序与改造接缝

约 25 分钟 · 前置：基础件七课 · 产出：按施工顺序从零讲出 NAP 的每一层及其动机；说清"重建 butterfly"时 NAP 给什么、你带什么、接缝在哪

前七课给了你全部零件。这一课换建筑师视角：**如果从零写一个 agent-platform，你按什么顺序造什么，每一步是被什么缺口逼出来的**。这不是历史复盘——你们要自己重建一个这样的平台，这个施工顺序就是你的施工图：NAP 的每一层为什么存在，决定了你的版本哪些层照抄设计、哪些要换方案。

施工八步

第 0 步 · 地基：一个 K8s 集群
缺口：agent 需要一个"能自愈、能伸缩、能声明式管理"的运行底座，自己从零写这些等于重造 K8s。
造：直接采用 K8s（自部署用 k3s）。你的平台从第一行代码起就是"K8s 之上的应用"。
对应：第 2–6 课全部 · NAP：self-host/get.sh（一条命令装 k3s + 平台）
第 1 步 · 最小可行：一个 agent 活在 pod 里
缺口：agent 进程直接跑在机器上会随机器死、无隔离、多租户互踩。
造：workspace pod 的形状——agent 容器（前沿 core 的适配器）+ 卷挂 /workspace + sidecar 们；外面套 Deployment 保它自愈。
对应：第 1、4 课 · NAP：internal/k8s-provider/workspace-spec.ts（pod 形状唯一真相源）
第 2 步 · 生命线：期望状态账本 + 收敛器
缺口：谁决定"该有哪些 workspace 在跑"？平台需要一个常驻的决策者——但直接调 K8s API 创建 pod 是命令式，重启/升级/缩容全要自己写。
造：平台自己的账本（PostgreSQL：workspace 表 + 期望状态）+ 一个收敛器（env-runner：盯着账本，翻译成 K8s 对象）。三层套娃的声明式：改平台账本 → 改 K8s 账本 → 现实收敛。
对应：第 2 课哲学 · NAP：routes/workspaces/write.ts 的 Control inversion 注释 + env-runner-k8s/
第 3 步 · 会话真身：SSE 拦截器
缺口：agent 的流式响应直通客户端的话，会话只存在于 pod 内存——pod 一死，历史全丢。
造：让响应流穿过平台：拦截器实时把消息/统计写入 PG。会话真身从此住在数据库，pod 降级为可替换的执行者——这是后面一切（缩到零、换副本、换 core）的前提。
对应：第 2 课"生死边界" · NAP：lib/sse.ts 的 createInterceptedSSEResponse
第 4 步 · 入口：HTTP API + chat 通道 + 四道关
缺口：多租户共用一套 pod，一条消息的调度要解决"这个会话没人在跑吗（租约）""这个 workspace 还装得下吗（容量）""它睡着吗（唤醒）""该找哪个副本（亲和）"。
造：chat API 入口 + 四关串联 + 断线重连。注意顺序有讲究：前两关不过，不花唤醒的钱。
对应：第 3、5 课 · NAP：services/chat/executeChat.ts（租约→容量→ensureWorkspaceRunning→pickReplicaForTurn）
第 5 步 · 成本：两种 serving 模式
缺口：大部分 workspace 大部分时间没人用，常驻 = 为闲置烧钱；但直接砍掉又伤延迟。
造：给用户开关——static（常驻秒回：单副本 Deployment + RWO 盘）与 auto-scaling（缩到零省钱：StatefulSet 稳定身份 + RWX 共享卷 + headless 逐副本寻址做会话亲和）。一条决策链从业务落到存储和 DNS。
对应：第 4、5、6 课 · NAP：static-workload.ts / auto-scaling-workload.ts / workspace-address.ts
第 6 步 · 能力插座：平台当 MCP 服务器
缺口：agent 需要沙箱、浏览器、记忆、文件共享——这些是平台的能力不是引擎的；写死在引擎里则换 core 全要重写。
造：control-plane 做 MCP 工具服务器（八工具族按请求注册），pod 内 mcp-forward 转发且 core 配置零凭证。能力与引擎解耦：换 core，工具不动。
对应：第 7 课 · NAP：mcp/tools.ts + internal/mcp-forward/
第 7 步 · 交付：文件从 pod 到用户
缺口：产出文件锁在集群里的 PVC 上，用户看不见。
造：pod 内 dufs 把 /workspace 讲成 HTTP → 平台代理 → 文件面板/下载/限时分享 URL。注意：不复制文件，是给现有数据开视图。
对应：第 1、6 课 · NAP：routes/workspaces/agent.ts + mcp/tools/export-file-url.ts
第 8 步 · 之后（NAP 还在长的部分，也是你要研究的接缝层）
多入口（channel-gateway 接微信/Slack、scheduler 定时）、teamwork（agent 互调）、builder mode（对话式搭建）、web UI 插件点、Applications/App Spec（2026-10 上游新主题：一份 spec 声明整个应用）。改造 butterfly 时，产品层的落点大概率在这些缝里。

生死边界（改造时的架构红线）

状态真身在哪pod 死了？
会话与消息PostgreSQL（SSE 拦截器实时写）活
/workspace 文件（含 agent HOME）workspace 专属 PVC活
容器内 /workspace 之外的一切pod 文件系统死
沙箱里的东西独立集群，超时自毁本来就要死

唯一的死亡点是删 workspace（三件套 + PG 同事务清理）。这条红线是改造设计的地基：任何新组件先回答"我的状态真身放哪、跟谁的生死绑定"。

你的施工：与 NAP 的关系（每个阶段做一次选择）

施工顺序讲完，回到你的工程。每个阶段你都要对 NAP 做一次三选一，并且把决策记下来：

关系什么时候选它代价
抄设计（自己写，照它的形状）想彻底理解、或需要深度定制的一层自己背维护成本
直接用（部署它的组件）商品化程度高、领域无关的件（如沙箱服务、浏览器服务）接受它的边界与升级节奏
fork（改它的代码自用）设计对但需要中管改永久承担合并上游的成本

路线图（rebuild/ROADMAP.md）的每个阶段都标注了"读 NAP 哪个文件"——先读后写，每个阶段一次三选一。诚实提醒：最容易犯的错是全选"抄设计"（把自己青或在大闸门型定制上），第二容易的是全选"直接用"（平台同质化，失去自建意义）——每个阶段独立判断。

检索练习

1. 施工顺序里，"会话真身进 PG"（SSE 拦截器）排在 serving 模式之前，因为它是后者的——
  1. 性能的保障
  2. 计费的依据
  3. 安全的前提
  4. 缩到零的前提
2. 平台账本（PG）与 K8s 账本（etcd）的关系是？
  1. 互为备份关系
  2. 两层递进套娃
  3. 同一个数据库
  4. 各管各无关联
3. MCP 工具服务器这层存在的最大意义是？
  1. 提升调用速度
  2. 节省模型 token
  3. 方便计费统计
  4. 能力与引擎解耦
4. 调度四关里，唤醒（ensureWorkspaceRunning）为什么排在容量门之后？
  1. 前两关不过就不必花钱启动
  2. 唤醒必须在选副本之后
  3. 租约要先于一切存在
  4. 历史原因无深意
5. 自建平台时，沙箱/浏览器这类与业务无关、商品化程度高的组件，最合理的选择通常是？
  1. 全部自己重写
  2. 直接用它的
  3. 永远不用它
  4. 全都 fork 一份
