Lesson 09 / ACP 模块 1/6 · 概念课

ACP 全景 — 三个角色与一场对话的形状

约 12 分钟 · 前置：第 7 课（MCP）、JSON-RPC 问答 · 产出：说清 ACP 解决什么、三方角色、一场对话的五个方法、与 MCP 的分工 · 下一课起全部动手

你在 agent-hub 里撞的墙（"不了解协议写不下去"）这门课补。ACP（Agent Client Protocol）是 Zed 发起的开放协议，目标一句话：让任何客户端（编辑器、IDE、平台）能驱动任何 agent——USB 之于外设。你的 acp-adapter 的 ws 端点，本质上就是"把 pi 变成一个讲 ACP 的服务"。

三个角色

Client（客户端）发起方：Zed 编辑器、IDE、你将来的 control-plane。决定"开哪个会话、发什么话、要不要中断"。
Agent（助手）被驱动方：LLM 驱动的助手进程（codex CLI、你的 PiBridge）。处理请求、产出流式更新。
Session（会话）对话的容器：一个 agent 可同时开多个 session，各自独立上下文。有独立的生命周期（新建/加载/删除）。
注意"谁是 Client"可能和直觉相反：NAP 的桥 spawn codex CLI 时，桥是 Client，CLI 是 Agent。角色由"谁发起谁响应"决定，不由谁更大决定。你的 acp-adapter 暴露 ws 端点时，你的 adapter 是 Agent 侧，Zed 是 Client。

一场对话的形状（本课核心，背下来）

所有通信都是 JSON-RPC 信封（你已学：id 配对请求响应、无 id 是通知）。一次完整的对话：

Client Agent（你的 adapter） │ ── request ──────────────────────────────→ │ │ initialize（握手：协议版本、认证方式、能力） │ │ ←──────────────── response ────────────── │ │ │ │ ── request: session/new ────────────────→ │ 开会话（cwd、MCP 服务器列表） │ ←──────── response: sessionId ────────── │ │ │ │ ── request: session/prompt（用户的话）────→ │ 一个 turn 开始 │ ←── notification: session/update ─────── │ "正在想…"（agent_message_chunk） │ ←── notification: session/update ─────── │ "调用工具 git diff…"（tool_call） │ ←── notification: session/update ─────── │ "工具结果…"（tool_call_update） │ ←── notification: session/update ─────── │ "答案是…"（agent_message_chunk × N） │ ←──────── response: stopReason ───────── │ turn 结束（end_turn / cancelled / …） │ │ │ ── request: session/prompt …（下一轮）─────→ │

五个方法名就构成骨架：initialize → session/new → session/prompt → session/update（通知）→ 响应携带 stopReason。流式输出的全部魔法就是那一串 `session/update` 通知——你在 JSON-RPC 课见过的"无 id 消息"。

何时带 id（一句规则 + 一张判定表）：发出消息前问"我需要对方回答我吗？"——需要 → request（贴 id 票根）；不需要、只是播报 → notification（无 id，且协议禁止回复它）。| initialize/session/new/session/prompt：要结果 → ✓ id | session/update：进度播报，不等回音 → ✗ | request_permission：要"允许/拒绝"的答案 → ✓ id |。外卖类比：下单（request）→ 骑手轨迹推送（notification × N）→ 送达（response）——同一个订单号悬置全程，通知流从旁流过，最后 response 带号回来收尾。

双向：Agent 也会反过来调 Client

上图只画了 Client 发起的箭头，但 ACP 是双向协议：Agent 可以向 Client 发独立的方法调用，最重要的是 `session/request_permission`——"我要执行这个工具/命令，允许吗？"Client 的用户点允许/拒绝，答案回到 Agent 继续干活。这就是 NAP 里 `onPermissionRequest` 回调（你的 adapter 自动选第一个选项那处）在协议层的真身。此外还有 `fs/read_text_file`（Agent 请 Client 帮忙读写它看不见的文件）、`terminal/*` 一族（请 Client 开终端）等——每一个都是协议预定义的独立方法，不用你发明，只需你决定何时发起、以及如何响应。它们发生在 turn 执行期间，但不是嵌在 prompt 里的子请求：同一条连接上方向相反的独立 JSON-RPC 往返，靠各自 id 配对。

传输无关：stdio 与 WebSocket

传输场景和你的关系
stdio（nd-JSON 流）Client 把 Agent 当本机 CLI 子进程 spawn，走标准输入输出了解即可（生态里 CLI 型 agent 的常见形态）。本项目已决策：只支持 SDK 型 core，不 spawn CLI——不用实现
WebSocketAgent 是网络服务，Client 远程连你的 M3：Zed 直连 adapter 的 ws 端点——本项目唯一要实现的传输

同一套方法、同一套信封，换传输不改语义——这就是为什么 SDK 把传输做成了可插拔层（transports 目录）。

与 MCP 的分工（两张插座，别混）

MCP（第 7 课）ACP（本课）
连接的两端agent ↔ 工具服务器客户端 ↔ agent
解决agent 怎么获得能力agent 怎么被驱动、被呈现
典型方法tools/list、tools/callsession/prompt、session/update

一个真实 agent 同时站在两张插座中间：向左（Client）说 ACP，向右（工具）说 MCP。NAP 的架构正是这么摆的——adapter 对 cp 说 ACP/SSE，mcp-forward 对工具说 MCP。ACP 还有 `mcp_servers` 透传（Agent 告诉 Client"我要这些 MCP 服务器"，由 Client 侧拉起并回连）——第 13 课展开。
