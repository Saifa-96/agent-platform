一、空间总图：一切都是嵌套

你的 Mac（本地环境） ├── kubectl / helm（客户端进程——无状态，一切信息来自 kubeconfig） └── Docker Desktop └── 容器（k3d 集群的"节点"，假扮一台机器） └── k3s 进程（单二进制 = 整个物业） ├── 账本（API server 入口 + 存储） ├── ① controller / ② scheduler（记账与派单） └── ③ kubelet（每节点一个，唯一动手的） └── containerd └── pod（最小调度单位：共享网络+卷的容器组） └── container（被隔离的进程，按镜像跑起来）

层级口诀：集群管节点，节点养 pod，pod 装 container；节点看 kubelet，pod 看共享，container 看隔离。kubectl 在环境边界外，靠一次 HTTPS 请求（经 Docker 端口映射/门房容器 → 节点:6443）跟物业说话。

二、三条主哲学（贯穿七课）

哲学一 · 声明式：写下期望，等收敛。你写的永远是"应该是什么"，不是"怎么做"——Deployment 的副本数、PVC 的申请单、甚至 Docker 保 k3s 活着的重启策略，全是同一个动作。推论：apply 是下单，不是收货（created ≠ Running，拉镜像要真实时间）。
哲学二 · 账本与订阅：系统内部没有电话，只有账本。①②③谁也不调用谁，全靠"改账本 → 推送给订阅者 → 各自反应"。这个模式你已遇见四次：etcd（集群账本）、kubeconfig（频道表）、helm 的 index.yaml（包目录）、以及 NAP 的 PostgreSQL（平台自己的账本）。
哲学三 · 生死边界：数据的寿命由"真身在哪"决定。pod 文件系统随 pod 死；/workspace 在 PVC 上活过 pod；会话真身在 PG。集群是最大生死边界——边界内全灭，边界外（镜像缓存、本地文件、外置存储）各活各的。NAP 里唯一的死亡点：删 workspace。

四、一条消息的旅程（浓缩版）

用户消息 → 通道（web/API/定时/webhook） ↓ control-plane 四关：会话租约 → 容量门 → 唤醒（ensureRunning，90s 冷启动）→ 选副本（亲和） ↓ 用户消息先落 PostgreSQL（SSE 拦截器实时持久化——会话真身不在 pod） ↓ HTTPS → pod 内 agent 适配器（ACP 包着的前沿 core） ↓ 模型决策：① 直接写 /workspace（PVC）② 调 MCP 工具（mcp-forward → cp → 沙箱/浏览器/记忆…） ↓ SSE 流回程，穿 cp 拦截器：消息/统计入库，广播给重连客户端 ↓ 交付：dufs（pod 内文件服务器）→ 文件面板/下载/分享 URL

详版（含每格的生死边界与代码锚点）在第 8 课：一条消息的旅程。

五、NAP 决策链速查（业务 → 技术的完整翻译）

业务：省钱（闲置零成本） vs 秒回（常驻热身） ↓ serving 模式：auto-scaling（缩到零） vs static（常驻单实例） ↓ 副本分布：1..N、散布多机 vs 永远单实例 ↓ ↓ 盘：RWX 共享（NFS，多机同挂） RWO 单机盘 ↓ 寻址：StatefulSet 稳定序号 + headless ClusterIP Service 足矣 → 会话亲和：重连找回"还是那个副本"

六、你踩过的坑（易错清单，来自真实问答）

挂载 ≠ 拷贝：FUSE/NFS/PVC 都是实时视图，数据从不落地复制。memory sidecar 是"现场翻译成 SQL"，不是下载。
controller ≠ kubelet：controller 在 control plane 记账（数数、登记 Pod 对象）；kubelet 在每节点动手（唯一拉镜像的）。一个集群一套 controller，一个节点一个 kubelet。
名字 ≠ 标签：metadata.name 是档案标题（给别人找声明用）；template.labels 是盖在 pod 上的章（selector 认领用）。K8s 只校验"章能对上认领标准"。
created ≠ Running：apply 只改账本；拉镜像、健康检查耗真实时间。等收敛用 rollout status / wait。
localhost:8080 化石：看到它 = kubeconfig 里没有可用 context（集群被删了）。k3d 删集群会顺手删 context。
代理吃 0.0.0.0：国内代理环境（Clash）+ k3d：kubectl 的请求被送进代理对 0.0.0.0 掐断（EOF）。修复：~/.zshrc 加 no_proxy。
流程图是角色图不是位置图：①②③的分工永远不变；住址因发行版而异（k3s 把五个角色压进一个进程）。
环境边界：kubectl/你在本地环境；control plane 在集群环境（节点容器内）。跨界的桥是一次 HTTPS 请求。

七、毕业自测（10 题，答不出回对应课）

1. pod 死而复生后 IP 会怎样？（第 5 课）
  1. 保持永远不变
  2. 立即变成两个
  3. 由管理员指定
  4. 换成一个新
2. 同一 pod 里的两个容器互相访问用？（第 1 课）
  1. 用 localhost
  2. 走公网地址
  3. 靠消息队列
  4. 写共享文件
3. auto-scaling workspace 用 StatefulSet，主要图它什么？（第 4 课）
  1. 更高的资源配额
  2. 自动免费备份
  3. 每副本独立盘
  4. 稳定的副本身份
4. 谁真正动手创建存储卷？（第 6 课）
  1. API server
  2. scheduler
  3. provisioner
  4. kubelet
5. PVC 状态从 Pending 变 Bound 意味着？（第 6 课）
  1. pod 已经就绪
  2. provisioner 已交货
  3. 申请被拒绝了
  4. 磁盘已经用满
6. headless Service 的 DNS 查询返回？（第 5 课）
  1. 各 pod 自己的地址
  2. 一个虚拟的 IP
  3. 报错说找不到
  4. 最闲的那个
7. 删掉一个 pod 后，Deployment 的期望值（spec.replicas 字段，即 READY 分数 3/4 里的分母）会怎样？（第 2、3 课）
  1. 完全没有变化
  2. 暂时减一随后恢复
  3. 变成三然后回四
  4. 触发了自动扩缩
8. 模型"调用"MCP 工具时实际输出的是？（第 7 课）
  1. 直接执行的代码
  2. 结构化的意图文本
  3. 一次网络的数据包
  4. 数据库里的语句
9. NAP 里 workspace 数据真正的死亡点？（第 6 课）
  1. pod 被销毁时
  2. 节点重启之时
  3. 用户登出账号
  4. 删除 workspace
10. kubectl apply 拿到 created 响应意味着？（第 2、4 课）
  1. 容器已在运行
  2. 账本已更新而已
  3. 镜像已经下载
  4. 健康检查已通过
