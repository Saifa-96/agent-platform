PVC 与 StorageClass —— 比 pod 活得久的磁盘

约 20 分钟 · 前置：第 1 课（挂载与卷）、第 3 课（RWO/RWX）· 本课产出：能按顺序讲出存储供给链的五个步骤，能说清 NAP 数据的生死边界 · 配套练习：exercises/0001-mini-env-runner

第 1 课里我们留了一条线索：pod 的文件系统会随 pod 一起消失，而 /workspace 里的文件却能存活，因为这些文件不在 pod 的文件系统里，而是挂在一块"卷"上。这一课拆解卷的机制。你会发现它仍然是声明式哲学的又一次应用——这是第三次遇到同一套思想，这次的对象是你的磁盘。

先看没有 PVC 的世界

假设 K8s 没有提供卷的抽象，你要给 agent 分配一块盘，就必须亲自做这些事：先弄清楚这个集群用的是什么存储技术（NFS？Ceph？云盘？），拿到服务器的地址和路径；然后自己创建一块盘，把它的具体地址写进 pod 的清单。这样做的后果是：清单和底层基础设施被焊死在一起，换一个集群就要修改所有清单。

这个问题和"必须自己指定 pod 落在哪台机器上"属于同一类问题，而 K8s 对这两件事的解决办法也是一样的：增加一层间接，把"要什么"和"怎么给"分开。你不需要声明"使用 NFS 服务器 X 的目录 Y"，正如你不需要声明"把 pod 调度到节点 2"；你只需要提出需求，剩下的事由别人决定。

三个对象，一条供给链

PVC（申请单）你写下的声明："要 10Gi、RWO 的一块盘"
PersistentVolumeClaim
→
StorageClass（供货规则）申请单由哪条供应链满足：NFS？云盘？CephFS？
背后是 provisioner（供货程序）
→
PV（交付的货）provisioner 真实创建的存储资源，
记录着数据真身的地址

三个对象的职责可以这样概括：PVC 是消费者提出的需求，PV 是供应商交付的货，StorageClass 是连接两者的供货规则。下面是它们各自的真实样子：

# PVC —— 你写的申请单，保存在你的 namespace 里
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: agent-workspace }
spec:
  accessModes: ["ReadWriteOnce"]
  resources: { requests: { storage: 10Gi } }
  storageClassName: nfs-nap        # 由哪条供应链供货（省略则使用集群的默认值）

# PV —— provisioner 交付的货（集群级对象，通常不需要你接触）
apiVersion: v1
kind: PersistentVolume
metadata: { name: pvc-abc123-agent-workspace }
spec:
  capacity: { storage: 10Gi }
  nfs: { server: 10.96.1.9, path: "/exports/xxx" }  # ★ 数据真身的地址就在这两个字段里
  claimRef: { name: agent-workspace }                # ★ 绑定记录：这块货交付给哪张申请单

# StorageClass —— 管理员部署集群时配置好的供货规则（你只消费，不管理）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: nfs-nap }
provisioner: nfs-subdir-external-provisioner   # 供货程序的名称
parameters: { archiveOnDelete: "true" }      # 删除 PVC 时先归档，而不是立即抹掉数据
reclaimPolicy: Delete

时间线：一块盘的一生

下面这条时间线把三个对象串成了一个完整的故事。学完这一课，你应该能做到不看资料、按顺序讲出这五步。

T0
你提交 PVC 申请单。此时它的状态是 Pending，意思是申请单已经递出，但货还没有到。
T1
provisioner 注意到这张 Pending 的申请单，自动完成三件事：在 NFS 服务器上创建一个子目录；生成一个 PV 对象，把子目录的地址记录进去；把这块 PV 绑定给这张 PVC。绑定完成后，PVC 的状态变为 Bound，相当于收货完成。
T2
你提交 Deployment，清单里通过 claimName 引用这张 PVC。pod 启动时，kubelet 拿着 PVC 的名字找到与它绑定的 PV，再按照 PV 里记录的地址完成挂载。从此，容器里的 /data 目录实际上就是 NFS 服务器上的那个子目录。
T3
pod 死掉重建，或者被调度到另一台机器，都不影响数据：新机器上的 kubelet 拿着同一个 PVC 的名字，找到同一块 PV，按照同一个地址挂载，看到的仍然是同一份数据。这一步就是整个机制存在的意义：pod 通过"PVC 名字"这个间接层取盘，而不是通过地址。地址、机器、pod 都在变，名字永远不变。
T4
你删除 PVC，此时 reclaimPolicy 开始生效：provisioner 会删除（或按配置归档）NFS 上的那个子目录。到这一步，数据才真正死亡。

收货是否完成，可以随时用一条命令查询：

kubectl get pvc agent-workspace

NAME             STATUS   VOLUME                       CAPACITY
agent-workspace  Bound    pvc-abc123-agent-workspace   10Gi
                 ↑已收货   ↑绑定的 PV 名称
这一课确实是六个基础件里最难的一篇：三个对象的职责彼此重叠；provisioner 在后台异步工作，"发货"的过程完全看不见；页面上还满是新名词。T0 到 T4 这条时间线，就是把名词串成故事的那条主线——先做到能按顺序讲出这五步，再回来做本页的测验。

RWO 与 RWX：选择供应链就是选择访问模式

第 3 课里你已经把 RWO 和 RWX 问得很透：RWO 表示同一时刻只允许一台机器挂载，块设备（云盘、Ceph RBD）只能工作在这种模式下；RWX 表示多台机器可以同时挂载同一块卷，NFS 这类网络文件系统才能做到。这里再补一个连接点：访问模式是 StorageClass 的能力，PVC 自己无法更改。因此，NAP 在创建 auto-scaling workspace 之前，要先检查环境里是否存在支持 RWX 的 StorageClass——没有它，多个副本就无法共享同一块 /workspace 卷。

NAP 的存储账本（对应真实代码）

事实对应代码
每个 workspace 拥有一块独立的 PVC，名字由纯函数派生：<workspace-id>-workspaceinternal/k8s-provider/support.ts:73
static workspace 使用 RWO 单机盘；auto-scaling workspace 使用一块 RWX 卷，并且不设置 volumeClaimTemplates——所有副本共享同一块卷，而不是各配各的auto-scaling-workload.ts
卷默认 10Gi，可以按 workspace 覆盖；扩容只增不减expandWorkspacePvc（static-workload.ts）
StorageClass 在创建时写入 PVC，之后不可更换——所以迁移的真实含义是搬运数据K8s 机制本身
删除 workspace 时，Deployment、Service、PVC 三者一起删除——这是数据真正的死亡点（对应时间线的 T4）static-workload.ts destroy()
自部署默认使用 NFS 供应链：nfs-subdir-external-provisioner 负责供货；单机部署时还会在集群内运行一个 NFS server，数据就落在那台节点的磁盘上self-host/manifests/nfs-server.yaml
对照 butterfly：你们的沙箱 pod 挂载的是一块全体共享的 PVC（K8S_PVC_CLAIM_NAME=data）——机制相同，区别在于"所有租户共用一块盘"和 NAP 的"每个 workspace 一块盘、各自限额"。本课的练习是必做环节：exercises/0001-mini-env-runner——亲手把 T0 到 T4 走一遍，第五课才算真正焊牢。
