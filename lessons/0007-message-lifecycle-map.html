Lesson 07 / 会师点（先学完 0001–0006 基础件）

一条消息的旅程 — NAP 全景地图

≈ 20 分钟 · 前置：pod/k3s/工作负载/Service/PVC/MCP 六课 · 产出：不看资料复述完整旅程 + 说出每类状态的存活层

你写过引擎的内部——turn 循环、工具注册、闸门，这些都是你的主场。平台设计的第一课不是学新零件，而是换观察位置：从"我怎么执行一个 turn"移到"系统怎么托管一万个 turn"。最好的办法是跟着一条消息走完全程，把每个组件的生死边界记在脑子里。这张地图之后的所有课程都在它的某个格子里加深。

四关的顺序有讲究：先占会话租约（一个 session 同时只能有一个 turn），再过容量门（auto-scaling 有并发上限，超了 503），然后才谈唤醒和选副本——前两关不过，后面的钱一分不花。

②到③之间还有一件关键事：用户消息先落 PostgreSQL，再 POST 给 pod。以及整个响应流不是直通车的——agent 的 SSE 穿过控制面的拦截器（lib/sse.ts），消息、统计、会话都在这里被实时持久化。这就是平台"看得到一切"的原因，也是断线重连、pod 中途死掉都不丢会话的原因。

三个生死边界（本课真正要记的东西）

状态真身在哪pod 死了？
会话与消息PostgreSQL（SSE 拦截器实时写）活
/workspace 文件
（含 agent 的 HOME：transcripts、skills）		workspace 专属 PVC（默认 10Gi）活
容器内 /workspace 之外的一切pod 自身文件系统死
沙箱里的东西独立集群，默认 1 小时自毁本来就要死

推论：pod 是牲口不是宠物——缩容、重建、升级、换 core 都不构成数据事件，所以平台敢把它随便杀。真正的销毁只有一条路径：删 workspace（PVC 和 PG 记录一起清）。

和 butterfly 的对照（你的锚点）

  • 调度四关 ≈ 你们的 turn-state 收场闸，但反向：你们闸的是"一步内别写坏"，平台闸的是"多租户下别挤爆"。
  • SSE 拦截器 ≈ 你们引擎里 session 持久化的位置，但被提到了 agent 进程外面——持久化属于平台，不属于引擎。
  • 沙箱"产物必须显式拉回" ≈ 你们 K8s 沙箱同一条纪律，NAP 把它写成了工具语义。

检索练习

现在合上上面的内容，凭记忆答。答错说明那一格还没进长期存储，回去看对应段落。

1. 消息到达 pod 之前，控制面依次过四关。第三关是？
  1. 占住会话租约
  2. 通过容量之门
  3. 唤醒沉睡副本
  4. 挑选就绪副本
2. pod 被销毁后，一定还活着的是？
  1. 会话消息记录
  2. 容器系统缓存
  3. 沙箱临时文件
  4. pod 进程内存
3. agent 转录文件（transcripts、skills）的真身在？
  1. pod 的内存里
  2. PVC 的卷上
  3. 浏览器本地里
  4. 沙箱的盘里
4. auto-scaling 工作区缩到零后，用户发来消息会？
  1. 报错说区已停
  2. 消息排队过夜
  3. 转给别区处理
  4. 冷启动再处理
5. agent 想用平台能力（如建沙箱），调用经过？
  1. 直连沙箱服务
  2. mcp-forward 一跳
  3. 写文件到 AFS
  4. 经 dufs 文件服
