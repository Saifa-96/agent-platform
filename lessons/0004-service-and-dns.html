Service 与 DNS — 找到总在搬家的 pod

≈ 15 分钟 · 前置：Lesson 03（Deployment/StatefulSet、label 认领）· 产出：说清两种寻址方式和 NAP 那个"故意不用 VIP"的原因

前两课留了一个没兑现的问题：pod 会死而复生（自愈），而每次复活都换 IP——IP 是调度时从节点"租"来的。可是调用方需要一个稳定地址。这对矛盾由 Service 解决——K8s 里名字最迷惑的对象（它叫 Service，但它不是"服务"，只是一张稳定的门牌）。

ClusterIP Service：一块稳定的虚拟门牌

🏷️ 门牌：my-agent → 虚拟 IP 10.96.1.5（VIP，Virtual IP）
集群内 DNS：my-agent.default.svc.cluster.local
▼ 请求到达门牌后，自动分发给名单里的 pod（轮询）
pod
10.244.2.7
pod（刚死了）
10.244.1.3
pod
10.244.3.9
▲ 死的自动除名、新生的自动进名单——门牌永远不用改

三件事记住就够：

  • 认领规则还是 label：Service 用 selector 挑 pod（还记得第 3 课清单里 Deployment 给 pod 盖的 app: my-agent 标签吗？Service 就认它）。同一条标签把 Deployment 和 Service 缝在一起。
  • 名单自动维护：只有活着且通过健康检查（Ready）的 pod 在名单里。pod 换 IP 无所谓——名单实时更新，门牌不变。
  • VIP 后面是轮询：请求一个一个分给名单里的 pod。单副本时无所谓；多副本时……记住这个伏笔。

Headless Service：不要门牌，要名册

另一种 Service 声明 clusterIP: None，叫 headless（无头——没有 VIP 这颗"头"）。它不给你虚拟门牌，DNS 查询直接返回每个 pod 自己的地址。配合 StatefulSet 还有一个关键福利：每个副本有带序号的稳定 DNS 名——

# StatefulSet db + headless svc db-h 的组合下：
db-0.db-h.default.svc.cluster.local   # ← 永远指副本 0（不管它死过几次、IP 换过几个）
db-1.db-h.default.svc.cluster.local   # ← 永远指副本 1

这正是第 3 课说的"稳定序号 → 稳定网络地址"的兑现处：身份（序号）变成了可寻址的名字。DNS 里的事都由集群内的 CoreDNS（一个跑在集群里的域名解析服务）照着账本实时回答。

NAP 的选择：两种都用，一处故意不用

static workspaceauto-scaling workspace
寻址ClusterIP Service（VIP）headless + per-ordinal DNS
为什么单副本，轮询无所谓——VIP 最省事多副本，轮询会坏事

多副本时轮询坏什么事？会话亲和（session affinity）：一个 turn 正在副本 2 的 agent 进程里跑着（内存里有现场），断线重连的下一个请求若被 VIP 轮询分到副本 3——那边没有这个正在跑的 turn，现场就断了。文件没事（大家共享同一块 RWX 卷，第 3 课），但正在执行的进程现场只在一个副本里。

所以 NAP 的路由（control-plane/src/lib/workspace-address.ts）是这样写的：会话绑定了哪个副本，就解析哪个副本的 per-ordinal DNS 名，精确投递；没绑定就挑任意就绪副本；一个都没有（缩到零）时解析 headless 名，等第一个 pod 就绪立即接上。代码注释原话："a VIP would round-robin across replicas and defeat session affinity"。

对照 butterfly：你们用 PM2 cluster 模式时也有同样的问题——请求落到哪个 worker、worker 里有没有这个会话的现场。你们在应用层解决；K8s 给的零件是 headless + 逐副本地址，让"会话跟着副本走"变成寻址层的事。

检索练习

1. pod 死而复生（自愈补回）后，它的 IP 会？
  1. 保持永远不变
  2. 立即变成两个
  3. 由管理员指定
  4. 换成一个新
2. ClusterIP Service 提供给调用方的是？
  1. 稳定虚拟门牌
  2. 更大的带宽
  3. 外网访问能力
  4. 数据持久化
3. Service 靠什么认领"哪些 pod 归我转接"？
  1. pod 的名字
  2. IP 段的范围
  3. label 标签选择
  4. 创建先后顺序
4. headless Service（clusterIP: None）的 DNS 查询返回？
  1. 一个虚拟的 IP
  2. 各 pod 自己的地址
  3. 报错说找不到
  4. 最闲的那个
5. NAP 的 auto-scaling workspace 不用 VIP，因为轮询会？
  1. 破坏会话亲和
  2. 消耗更多费用
  3. 拖慢 NFS 卷
  4. 用尽 IP 地址
6. turn 在副本 2 上跑，断线重连后必须？
  1. 随便找个副本
  2. 找回副本 2
  3. 重启整个集群
  4. 重新排队一次
