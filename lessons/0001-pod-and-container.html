Pod 与容器 — agent 住的房间

≈ 15 分钟 · 前置：无 · 产出：说清 镜像→容器→pod→节点 四层关系，以及 NAP 的 agent pod 里住着谁

NAP 的一切，最后都是"某个 pod 里的某个进程在干活"。你之前把 k3s 理解为"部署公寓"——方向是对的，这组课就把这个公寓一层层拆开。今天只拆一间：agent 住的房间（pod）。

图纸与房子：镜像和容器

先分清两个词，后面所有内容都压在它俩身上：

  • 镜像（image）= 图纸。一份只读的打包模板：代码 + 运行时 + 依赖，分层冻结而成。它自己不运行，放多久都不会变。
  • 容器（container）= 按图纸建的房子。镜像的一次运行实例：一个被 Linux 内核隔离起来的普通进程——看得见独立的文件系统（来自镜像），有自己的资源限额（CPU/内存），互相看不见对方的进程。

关键认知：容器不是虚拟机。没有模拟硬件、没有装第二个操作系统，它就是一个进程，只是被内核用 namespace（隔离视野）和 cgroup（限额）圈了起来。所以它启动是秒级的——和启动一个普通进程差不多。

对照 butterfly：你们的曦曦引擎是一个 Bun 进程跑在 PM2 里。"容器化"做的事，就是把这个进程连同它依赖的 Bun、node_modules 一起按图纸打包，让它在任何机器上都能原样跑起来——不用那台机器装过任何东西。

Pod：K8s 的最小调度单位

K8s 不直接调度容器，它调度的单位是 pod：一个或多个容器的组合，满足——

  • 同 pod 的容器共享网络：彼此用 localhost 互通，对外一个 IP；
  • 同 pod 的容器共享存储卷：大家挂同一块盘，看到同一份文件；
  • 同生共死、一起调度：k8s 不会把一个 pod 拆到两台机器上。

为什么要有这一层？因为有些进程天然需要住在一起——比如主程序 + 一个给它做辅助的伴随进程。这种伴随容器的英文名是 sidecar。名字来历：摩托车边斗——绑在主车旁边、主车到哪它到哪、有自己的座位但不是司机。同 pod 的辅助容器正是这个角色：跟随主容器同调度同生死，只做辅助。

打开 NAP 的真实房间

NAP 每个用户 workspace 就是一个 pod。它的形状定义在一个文件里（internal/k8s-provider/workspace-spec.ts），简化后长这样：

# 一个 workspace pod（公寓里的一间房）
containers:
  - name: agent          # ← 主人：Claude Code / Codex / Goose 之一的适配器
  - name: afs           # ← sidecar：把跨 agent 共享盘挂成 /mnt/afs
  - name: memory-fuse   # ← sidecar：把记忆库（存在数据库里）挂成 /mnt/memory
volumes:
  - name: workspace     # ← 挂到 /workspace 的持久磁盘（第 5 课细讲）
先解几个名字。 /mnt：Linux 惯例的“挂载点”目录——挂载（mount）= 把另一块存储（磁盘/网络文件系统/数据库）接到目录树上。/workspace：NAP 约定的 agent 主工作目录，持久盘挂在这。FUSE：把“别处的东西”（网络存储、数据库）伪装成本地目录的技术——注意是实时翻译，不是拷贝：你读文件时它才去查真身，数据从不落地。dufs：一个开源的极简文件服务器（Rust 单二进制），跑在 agent 主容器里，把 /workspace 暴露成 HTTP——你的文件面板/下载就是它在递文件。
POD（一个 workspace）
agent 容器前沿引擎适配器 + dufs（把 /workspace 讲成 HTTP）
HOME 指向 /workspace/.home
afs sidecar把跨 agent 共享盘
伪装成本地目录 /mnt/afs
memory sidecar把数据库里的记忆库
伪装成 /mnt/memory
💾 workspace 卷 → 挂在 /workspace（文件的真身所在，比 pod 活得久）

注意两个设计动作：① agent 的 HOME 被指到 /workspace/.home——transcripts、skills 全落在卷上而不是容器文件系统里，pod 死了它们不死；② 两个 sidecar 各自把“远处的数据”（共享盘、数据库里的记忆）用 FUSE 翻译成本地目录（/mnt/afs、/mnt/memory），dufs 再把 /workspace 翻译成 HTTP。方向不同：dufs 是出口（外面的人看 agent 的文件），两个 sidecar 是入口（agent 用本地姿势用远处的东西）。都没有拷贝数据，都是实时翻译——agent 容器活得像个普通 Linux 用户，对分布式一无所知。三个容器，一个视野，这就是 pod 这个抽象的用处。

sidecar 把远处的数据“翻译”成本地目录、dufs 把目录翻译成 HTTP——agent 容器对分布式一无所知，这是个重要的设计哲学，第 7 课会看到它的全部回报。

楼层：节点

pod 最终要落在某台真实机器上跑，这台机器叫节点（node）。一栋公寓（集群）= 许多节点 + 一个物业（k8s 控制面，下一课的主角）。至于 k3s：它是 K8s 的轻量发行版——把整个"物业系统"压缩成单个二进制，一台 Linux 机器就能开张。NAP 的 quick start 一条命令装的就是它。物业怎么运作，是下一课的事。
