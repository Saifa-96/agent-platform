Deployment 与 StatefulSet — pod 的两种管理员

≈ 15 分钟 · 前置：Lesson 02（期望状态）· 产出：判断任何服务该用哪种，并说清 NAP 为什么两种都用

上一课结尾说：你写下期望状态"应该有 3 个 pod"，剩下交给收敛。这课回答：具体是谁在读这句话、按什么规则管 pod？K8s 里管 pod 的东西叫工作负载控制器（workload controller），你只需要认识两种——恰好 NAP 每种都用了一个。

注意：workload controller 不是 kubelet。它们是两层不同的循环：controller 住在 control plane，只负责"数副本数量，缺了就在账本里登记新 pod 对象"——纯记账，不碰容器；kubelet 住在每台机器上，读到"这个 pod 归我管"才真正拉镜像、启动容器。中间还有 scheduler 给 pod 挑机器。链条上没人直接调用谁，全靠改账本协作（上一课哲学的内部贯彻）。controller = 总部数人头的调度员，kubelet = 楼层管家。

从"写下期望"到"容器跑起来"：完整流程图

你：写下 Deployment ——「期望：3 个副本」
▼ 写入（唯一入口 API server）
📒 账本（etcd） —— 所有人的唯一中转站，没人打电话，只读写这里
control plane（总部）
① Deployment controller（数人头）
读账本：期望 3，现只有 2 个 pod 对象，差 1
→ 通过 API server 在账本里登记 1 个新 pod 对象
纯记账，没碰任何容器
② scheduler（派单员）
读账本：发现 1 个新 pod 没定机器
→ 挑机器：「pod-x → 节点 2」写进账本
▼ 账本变化，被对应节点的 kubelet 监听到（不是被通知，是自己一直在看）
节点（楼层）
③ kubelet（楼层管家）
读账本：「pod-x 归我管」
→ 拉镜像、创建容器、上报状态
全链条唯一动手的环节
▼ 容器就位，状态回写账本

↺ 自愈也是同一条链：pod 崩了 → 所在机器的 kubelet 重启它；整个机器挂了 → controller 发现账本里少了，重新走①②③在别的机器补上。没有"报警-修复"系统，只有永不停歇的循环。

「写下 Deployment」的具体形态：YAML 清单

"workload controller"一词指两层：控制器软件（K8s 自带的通用进程，所有 Deployment 共用一个，你不用写）和你的声明（一个 YAML 清单文件，你真正"写下"的东西）：

apiVersion: apps/v1
kind: Deployment        # 声明的种类："我要一个 Deployment"
metadata:
  name: my-agent
spec:                   # 期望状态：你真正"写"的内容
  replicas: 3           # ← 流程图里的"期望 3 副本"
  selector:
    matchLabels: { app: my-agent }  # 认领规则：带此标签的 pod 归我数
  template:             # pod 的模子（第 1 课的图纸）
    spec:
      containers:
        - name: agent
          image: my-agent:1.0

提交：kubectl apply -f deployment.yaml → API server → etcd → 上面的链条开动。YAML 只是给人写的序列化格式（线上跑 JSON），程序可以跳过它直接构造对象——NAP 就是这样：internal/k8s-provider/static-workload.ts 里 createNamespacedDeployment(...) 用 TypeScript 构造对象直接提交，NAP 没人手写 YAML，写 YAML 的角色被 env-runner 的代码取代。

分水岭：副本可不可以互换

选哪种管理员，只看一个问题：你的多个副本（replica）是不是彼此等价的"无名氏"？

Deployment

app-7f9c8b-x2vklapp-7f9c8b-p9qz4app-7f9c8b-k3m8w
  • 副本无名、等价、可互换：名字带随机尾巴，谁死都一样，补一个就行
  • 内置滚动升级：新的起、旧的下，服务不中断；可回滚
  • 适合无状态（stateless）服务——典型的 Web API

StatefulSet

db-0db-1db-2
  • 副本有身份：稳定序号 0、1、2，死而复生还是原来的编号
  • 有序启停：按编号顺序起、按编号倒序停
  • 通常每个副本挂自己的盘——数据跟着身份走
  • 适合有状态（stateful）服务——典型的数据库
名字来历：Deployment = "一次部署"的名词化——你声明一次部署应有的样子。StatefulSet = stateful（有状态的）+ set（一组）——"一组有身份的东西"。判断口诀：**副本死了，随便补一个没人发现 → Deployment；副本死了，必须"还是它" → StatefulSet。**

为什么数据库需要身份？想象 PostgreSQL 主从：db-1 是从库、攒着自己的复制位点——它死了补一个全新 pod 进来没用，必须还是"db-1"、接上原来那份数据。身份+盘跟着走，这就是 StatefulSet 存在的理由。

NAP 的两种用法（真实代码）

NAP 恰好一边一个，而且用法都不是最典型的——值得细看：

为什么常驻单实例，最简单形状要稳定身份做会话亲和，不要独立盘
代码internal/k8s-provider/static-workload.tsinternal/k8s-provider/auto-scaling-workload.ts

两个提前一分钟的词：RWO（ReadWriteOnce）= 卷同一时刻只能被一台机器（K8s 节点）挂载——注意限制单位是机器不是 pod：同机器上的多个 pod 可以共享，跨机器不行（挂载是机器内核执行的动作，pod 只是住在机器上用现成的）；RWX（ReadWriteMany）= 多台机器同时挂同一块卷（NFS 支持，因为数据真身在 NFS 服务器、各机器只挂网络客户端视图；块设备做不了——两个内核同写一个文件系统会损坏）。细节第 5 课展开。

注意 NAP 用 StatefulSet 的姿势：要了身份，没要独立盘。经典用法是"每副本一块自己的盘"（数据库），NAP 反着来——所有副本挂同一块共享卷。它图的只是稳定序号带来的稳定网络地址（第 4 课的主角）：一个会话被路由到副本 2，断了重连还能找到"还是副本 2"。这是对 StatefulSet 的创造性挪用，记住这个例子，比记住教科书定义有用。

检索练习

1. Deployment 管理的多个副本之间，关系是？
  1. 完全等价可换
  2. 各有自己编号
  3. 严格的主从
  4. 大小各不相同
2. StatefulSet 的副本命名形式是？
  1. 随机字符串尾
  2. 带稳定序号
  3. 按用户来命名
  4. 由 IP 所决定
3. PostgreSQL 主从集群（每个实例绑自己的数据）该交给谁管？
  1. Deployment
  2. CronJob
  3. 裸 Pod
  4. StatefulSet
4. NAP 的 static workspace（常驻单实例）由谁保证存活？
  1. StatefulSet
  2. 裸 Pod 直建
  3. Deployment
  4. PM2 守护
5. NAP 的 auto-scaling workspace 用 StatefulSet，主要图它什么？
  1. 更高的资源配额
  2. 自动免费备份
  3. 每副本独立盘
  4. 稳定的副本身份
6. auto-scaling 的多个副本共享同一块 RWX 卷，说明这些副本？
  1. 数据各管各的
  2. 看同一份文件
  3. 互相不能通信
  4. 永远只有一个跑
