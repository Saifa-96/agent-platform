Lesson 02 / 基础件 2/6

k3s 与期望状态循环 — 物业的记账本

≈ 15 分钟 · 前置：Lesson 01（pod）· 产出：说清"声明 vs 命令"两种哲学，以及 NAP 为什么永远不亲手创建 pod

上一课你认识了房间（pod）。这一课认识物业：pod 会死、会被搬迁、会被手动删掉，那么谁保证"该有的还在、该跑的还跑"？答案是一套哲学，而且 NAP 整个平台就压在它上面——理解了这课，后面所有课的"为什么"都会变简单。

两种做事的方式：命令 vs 声明

你平时写代码是命令式的：`起进程`、`杀进程`、`出错了再起一个`——每一步都是你发出的动作，出事靠你（或你的脚本）补救。

K8s 用的是声明式：你只写下期望状态（desired state）——"这个系统应该长这样"——然后有一个永不停歇的循环负责把现实推成那个样子。

🌡️ 恒温器比方：命令式 = 觉得冷了开暖气、觉得热了关掉，全天盯着；声明式 = 设 22°C，剩下交给恒温器：它不停地量温度、比较、修正。你给的是"目标"，不是"动作"。

物业的三个角色

角色是谁干什么
API server物业前台唯一入口：所有读写都经它，期望状态记在它身后的账本里
etcd记账本分布式键值库，存着整个集群的"期望 + 现状"。名字来历：分布式版的 /etc 配置目录（Linux 系统配置文件的惯例目录，见术语表）
kubelet每层楼的楼层管家跑在每个节点上的代理，真正启动容器的就是它。名字来历：little kube，"小管家"。
注意一个常见误解：control plane 从不亲手启动容器。它只是记账和发通知；启动容器的是各节点上的 kubelet。所以哪怕 control plane 挂了，已经在跑的 pod 照跑——只是没人纠偏了。

循环：reconcile（收敛）

这个不停歇的循环叫 reconcile（收敛/调和）。每一圈三步：

观察现实里有几个 pod？
→
对比期望 3 个，现实 2 个，差 1
→
行动让 kubelet 再起 1 个
↻

于是出现 K8s 最著名的性质：自愈。你手动删掉一个 pod？下一圈循环发现少了，自动补回。不是谁"监控报警后修复"，是记账本哲学的必然结果——现实只要偏离期望就会被推回去。

对照 butterfly：你们的 PM2 重启策略、看门狗脚本，是"出事 → 补救"的命令式修复；K8s 把修复做成了常驻循环，没有"出事"这个概念，只有"偏离"。

k3s：单机版物业

k3s = 轻量版 K8s 发行版（Rancher 出品）：把整个物业系统压缩成一个二进制，账本用内嵌 SQLite 替掉 etcd，一台 Linux 机器就能开一个完整集群。名字来历是个缩小玩笑：k8s 表示"k 和 s 中间 8 个字母"（**K**ubernete**s**），k3s 中间只剩 3 个——小一号的 Kubernetes。

NAP 的 quick start 一条命令装的就是它：单机 k3s + 整套平台。生产可以换正式集群，对 NAP 来说无差别——它只跟"标准 K8s 接口"对话。

NAP 站在这套哲学的哪里

现在把镜头拉回 NAP。第 7 课你会看到全图，这里只记一件事：

NAP 的 control-plane（平台服务）从不亲手创建 pod。它做的事是：往数据库里写一条期望状态——"workspace X 应该在跑"——然后 env-runner（NAP 在集群里的手臂）监听到这条记录，翻译成 K8s 的声明（一个 Deployment），交给 K8s 去收敛。

真实代码注释原文（control-plane/src/routes/workspaces/write.ts:238）：

// Control inversion (P1): record desired state; the env-runner creates the pod.
// （控制反转：只记录期望状态；env-runner 去创建 pod）

这是一层套娃的声明式：NAP 对自己的手臂（env-runner）声明，env-runner 再对 K8s 声明，K8s 对现实声明。每层只写"应该是什么"，不写"怎么做到"。缩容、升级、pod 崩溃重启、换集群——在这个模型下全是同一件事：改账本，等收敛。

检索练习

1. 集群里真正启动容器的角色是？
  1. API server
  2. 节点上的 kubelet
  3. etcd 账本
  4. NAP control-plane
2. 想让系统跑 3 个副本，声明式的做法是？
  1. 手动连起三个
  2. 写脚本盯数量
  3. 写下应有三个
  4. 定时巡检补齐
3. 有人手动删掉了一个 pod，接下来会发生？
  1. 循环自动补回
  2. 永久消失掉了
  3. 集群停止服务
  4. 等人工去恢复
4. k3s 和标准 K8s 的关系，最准确的说法？
  1. 另一套新协议
  2. 云厂商收费版
  3. 容器运行时的一种
  4. 轻量的发行版本
5. NAP 的 control-plane 想"启动一个 workspace"，它实际做的是？
  1. 直接创建 pod
  2. 写一条期望状态
  3. 调用 kubelet 接口
  4. 发消息给管理员
